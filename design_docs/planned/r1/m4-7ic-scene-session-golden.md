## Problem

AC5 has only ever been a one-off scratch run. On `caf7c85` (AILANG v0.54.6, mission log iteration 29), `make replay SESSION=<scene session>` showed VM = interpreter, with VM 117.69 s and interpreter 2,107.46 s, and exited 2 because there was no golden (V23). Nothing in `make test` replays the scene session, so a sim change that breaks it would land green. Four facts measured at HEAD shape the design:

1. **The default playthrough has no `record` intent.** `make playthrough` (`SCRIPT ?= tests/playthrough_min.json`, `AI ?= none`, V1) asks the AI only when `ai_mode != "none"` (V3). Its 2,426-line session has 0 `record` intents. `AI=stub` gives 2,428 lines: the same session plus one `ai_open` and one `record` (V18). **The golden is therefore recorded from `AI=stub`.**
2. **The session log is the sim's input stream**, teed line for line in `SimBridge._write` (V2). A committed copy replays without Godot, so its golden does not depend on Godot. The playthrough is also byte-reproducible: two `AI=stub` runs gave the identical sha256 `ab44d47c…` (V19).
3. **The naive placement costs the interpreter run twice.** `make replay` runs every top-level `tests/replays/*.ndjson` on both engines. It is a prerequisite of `make test` and of `ci-fast` (V9), and it fails any case that has no golden for the current architecture (V7). A scene log dropped into `tests/replays/` would add the interpreter run, 1,403 s measured here (V20), to `rig/full`, which takes 66–77 min against a 5,400 s watchdog (V10). It would also add that run to GitHub's x86_64 fast tier, which has no x86_64 golden and would therefore fail.
4. **Archive unlocks need the input beside the output.** `codexUnlocks` on the replayed output alone prints `codex-unlocks=FAIL`: it credits `photon-drive` to `first_commit`. `sceneCodex`, which reads `session.ndjson` and the `states.ndjson` beside it, prints `PASS` for all 8 expected ids when `states.ndjson` is the replayed VM output (V21).

## Goals and non-goals

**Goals:** a committed scene log generated by the real playthrough; an arm64 golden recorded through `make replay-record`, which refuses to record unless VM = interpreter; a VM-only check in `make test`, with a positive control; a named, greppable x86_64 behaviour; and the evidence a reviewer needs.

**Non-goals:** running the interpreter in `make test` or `ci-fast` (D-125); an x86_64 golden recorded on x86_64 (see Design); any change to the sim, the scene or the playthrough driver; re-recording the existing replay cases.

## Design

### Placement: `tests/replays/scene/`, which `make replay` does not walk

`all_cases` lists only the top level of `tests/replays` with `os.listdir` (V5). The existing `compat-2.0/` subdirectory holds 6 `.ndjson` files that `make replay` never treats as cases. A new tests/replays/scene/ is therefore invisible to make replay and ci-fast (V5, V9, V22). It is also invisible to make replay-record LOG=all: the recipe passes `LOG` to `replay.py --record`, `--record all` expands through the same top-level `all_cases`, and no workflow invokes it (V33). `--session PATH` and `--record PATH` already accept a log anywhere and look for its golden beside it: for a `.ndjson` path, `case_of` builds the golden path from the log's own directory (V32).

| File | Made by | Content |
|---|---|---|
| `m4_scene_session.ndjson` | `make scene-session-fixture` | the sim input of `make playthrough AI=stub` with the min script, copied byte for byte (2,428 lines, 187,139 bytes, sha256 `ab44d47c…` today) |
| `m4_scene_session.input.sha256` | same target | the `shasum -a 256` line for the input |
| `m4_scene_session.state.arm64.sha256` | `make replay-scene-record` (`replay.py --record`) | the digest golden. The VM output is 83,297,783 bytes, over `DIGEST_OVER` = 256 KB (V8), so only its sha256 (`77f7ec49…`) is committed |
| `m4_scene_session.record.txt` | same target (tee) | the `replay:` version line and the `recorded …` summary line |

**Input lines versus replies (V28).** The input has 2,428 lines: `hello`, `new_game`, 2,425 `input` lines and a final `{"v":2,"type":"quit"}`, with no blank lines. `sim/ship.ail` answers each non-blank line before the first `quit` once and does not answer the `quit` itself. `replay.py` checks this with `expected_replies(log)`. The VM output is therefore **2,427 replies** (2,427 newline-terminated lines), 83,297,783 bytes. Everywhere below, "replies" means VM output lines and "input lines" means lines of the committed log. The input that V20 recorded is this fixture byte for byte: same sha256, same 2,428 lines (V27).

**Pinning the input.** There is no `.gitattributes` today (V14). Add `tests/replays/scene/*.ndjson -text`, so git never converts line endings. `make replay-scene` checks the input against `.input.sha256` before it replays, and a one-byte change to a scratch copy must fail that check (the input pin control). The input is never hand-typed. Only `make scene-session-fixture` writes it.

### Harness: `tools/replay.py` (role `harness`, V4; no new `*.py`)

- **`--vm-only`.** `verify` runs only the bytecode VM and skips the VM-vs-interpreter comparison. It keeps the reply-count check and the golden check. The case line ends `vm-only (VM = interpreter proven at record time)`. The run writes only `<scratch>/NAME.vm.ndjson`. The scratch default is `.godot/tmp/replay`, so the file is `.godot/tmp/replay/m4_scene_session.vm.ndjson` = `$(SCRATCH)/replay/m4_scene_session.vm.ndjson` (V31).
- **x86_64.** Under `--vm-only` only, when `NAME.state.<arch>.*` is missing and an arm64 golden exists, the harness compares against the arm64 golden and prints `replay vm-only: no <arch> golden for NAME; compared with the arm64 golden`. This is a real comparison, not a skip. All 12 committed arm64/x86_64 golden pairs are byte-identical today (V17). None of those 12 cases is a full 83 MB scene session, so this extrapolation is an assumption with the #153 CI-record as remedy, not a verified fact. A failure on x86_64 would be a cross-architecture divergence to report upstream; the remedy is the existing precedent of an x86_64 golden recorded on CI from a throwaway draft PR (#153). Without `--vm-only`, a missing golden still fails exactly as it does now.
- **Positive control.** `--positive-control` combined with `--vm-only` **reuses the VM bytes of the real check** against a copy of the golden in `<scratch>/positive-control/`, confirms that the clean copy passes, flips one byte in the golden copy (or output), and requires exactly one `golden …` failure. It makes no second sim run. It prints the existing control's exact line, `replay positive control: one-bit golden-copy divergence detected` (`replay.py:413`, V30), so one pattern matches both controls. The existing control without `--vm-only` is unchanged.
- **`--sim-only`** also asserts that the argv carries exactly `--caps IO`.
- **Record summary.** `record` prints `recorded PATH (R replies, B bytes, sha256 H, VM x s, interpreter y s)`. The fields are:
  - PATH: the golden written, relative to the root;
  - R: `out.count(b"\n")`, the VM output's line count, which equals `expected_replies(log)`;
  - B: `len(out)`, the VM output's bytes;
  - H: the full 64-hex sha256 of the VM output, which is also what the digest golden holds;
  - x and y: wall seconds of the VM and interpreter runs.

  Today it prints `(N lines, VM x s, interpreter y s)`, where N is that same reply count (V28). It still refuses on VM ≠ interpreter or on R ≠ `expected_replies` (V6).
- **`--arch`** already exists (`replay.py:374`, V29). AC7 uses it to exercise the x86_64 path on the rig.
- **Tests.** `tools/test_replay.py` runs against `tests/fixtures/fake_ailang.py` (V26), which gains a `FAKE_LOG` env var that appends each invocation's engine. New cases in a `VmOnly` class:
  - vm-only passes and never invokes the interpreter;
  - with no own-arch golden it falls back to arm64 and prints the named line;
  - with no golden at all it fails;
  - the vm-only positive control catches a one-byte flip with no extra sim run;
  - record prints bytes and sha256.

### Make targets (all in `mk/m45.mk`, which the Makefile includes; V25)

- **`scene-session-fixture`** (never in `make test`). It runs `$(MAKE) playthrough AI=stub PLAYTHROUGH_OUT=$(SCRATCH)/playthrough/scene-golden`, copies `session.ndjson` to `tests/replays/scene/m4_scene_session.ndjson` and writes `.input.sha256`. It prints `scene fixture: lines=L bytes=B sha256=H record=1 ai_open=1 commit=2 new_game=1 quit=1`, with each count taken by grep and checked. With `CHECK=1` it copies nothing: it `cmp`s a fresh playthrough against the committed file and prints `scene fixture: identical to a fresh playthrough`.
- **`replay-scene-record`** (never in `make test`). It runs `env -u AI_LIVE AILANG=$(AILANG) python3 tools/replay.py --record tests/replays/scene/m4_scene_session.ndjson`, and the `^replay:` and `^recorded` lines are teed to `.record.txt`. The VM and the interpreter run concurrently, about 24 min on the rig (V20).
- **`replay-scene`** (**`test: replay-scene`**, not in `ci-fast`) runs these steps in order:
  1. `shasum -a 256 -c` against the input pin, then the input pin control, which prints `scene input pin control: one-byte change detected`.
  2. The input shape: `"k":"record"` ≥ 1, `"k":"ai_open"` ≥ 1, `"k":"commit"` = 2, each with the control `"type":"input"` > 0 in the same command.
  3. The sha256 in `.record.txt` must equal the digest in `.state.arm64.sha256`.
  4. `env -u AI_LIVE AILANG=$(AILANG) python3 tools/replay.py --sim-only --vm-only --positive-control --session tests/replays/scene/m4_scene_session.ndjson`.
  5. Archive unlocks in the **replayed** stream. In `$(SCRATCH)/replay-scene/`, `ln -sf` the committed input as `session.ndjson` and step 4's `$(SCRATCH)/replay/m4_scene_session.vm.ndjson` as `states.ndjson`. Symlinks avoid copying 83 MB, and `sceneCodex` reads through them (V31). Then run `sceneCodex` (`sim/tools/session_audit.ail`, against `tests/expected_unlocks.json`), and require `codex-unlocks=PASS`.

  It ends with `replay-scene: PASS (VM only; interpreter proven at record time, see m4_scene_session.record.txt)`.

### AI process count 0

Today the claim holds by construction; nothing measures a process count. `parity-m4` runs `replay.py --sim-only`, which asserts that the only command it builds is `sim/ship.ail` and prints that no count is measured (V12, V24). `make replay-noai` measures `AiBridge.launch_count == 0`, but only for the Godot replay of `ai_stub_session`.

The new check keeps the construction argument and adds two type-level facts:
- the replay grants only `--caps IO`, and the harness now asserts that;
- the sim's entry is `export func main() -> () ! {IO}` (V13), and no tracked `.ail` imports `std/process` (V15). AILANG's effect checker rejects a `Process` use under an `{IO}` row. A probe calling `std/process.exec` from a `! {IO}` main fails with "Missing effects: Process", and the same probe with `{IO, Process}` passes (V16).

`replay-scene` greps that signature and prints `scene effects: main ! {IO}, --caps IO`. The recorded `ai_open` and `record` intents are bytes in the input, and nothing dispatches them.

### Budget

All figures are measured on this rig (V20):
- the VM alone takes 59.6 s, and 97.2 s next to the interpreter;
- the interpreter takes 1,403 s on v0.54.18, against the inherited 2,107 s on v0.54.6;
- `sceneCodex` takes 2 s.

`replay-scene` costs one VM run, the codex scan and two shasums of an 83 MB file. Allowing for load, that is at most about 120 s, roughly 2 % of the 5,400 s watchdog, against a measured `rig/full` of 66–77 min. GitHub's fast tier is unchanged. A release tag runs all of `make test` on ubuntu x86_64 (`release.yml` calls `ci.yml`, whose `full` input defaults to true; V11). There the check runs VM-only against the arm64 digest and prints the named line.

### Review of the record (S2's PR body)

The reviewer pastes and checks:
- the `.record.txt` lines: AILANG v0.54.18, arm64, 2,427 replies, 83,297,783 bytes, the full sha256, and both times. The record exists only if VM = interpreter.
- the `scene fixture:` line showing `record=1 ai_open=1 commit=2`, and `make scene-session-fixture CHECK=1` reading `identical`.
- `codex-unlocks=PASS` with the 8 ids, from `make replay-scene`.
- both positive-control lines.
- that no new target sets `AI_LIVE`, that each one that runs AILANG or `replay.py` carries `env -u AI_LIVE`, and that `sh tools/ai_live_guard.sh .` returns rc 0.

**When the sim's output changes on purpose,** `replay-scene` fails with the sha mismatch and the scratch path of the VM output. The fix is `make replay-scene-record` on the rig (about 24 min) and a reviewed change to the digest. A change to the scene leaves the committed input valid. `CHECK=1` reports the drift, and the fixture is only re-generated by a deliberate `make scene-session-fixture`.

## Risks and mitigations

- **Re-record cost.** Any change to the sim's output now needs a 24-minute record on the rig. *Mitigation:* the failure names the target and the scratch output. Sim changes that alter outputs already re-record every digest golden; this adds one wait, not a new kind of step.
- **An x86_64 divergence on a release tag.** *Mitigation:* the named line identifies it, and the CI-record precedent (#153) is the remedy. All 12 golden pairs are identical today.
- **Rig load.** The timings were taken at 1-min loads of 1.6–3.6, alongside a concurrent playthrough for about 160 s of the interpreter run. *Mitigation:* the about 120 s ceiling is twice the standalone VM time.
- **The protocol changes the input format.** *Mitigation:* the sim already accepts old logs (`replay-compat`). If it ever stops, regenerate with `make scene-session-fixture` and re-record, as a reviewed diff.
